## 1. 导论：叫「算法组」还是「视觉组」

- 两个名字指的基本是同一批人——早期干的事就是图像处理、找目标、算自瞄。
- 后来规则在变、机器人功能在变、队伍水平也在变，只喊「视觉组」盖不住了：除了看图，还得做状态估计、决策之类的事。
- 我的理解：**视觉组**强调的是「走计算机视觉这条路」，**算法组**强调的是「负责范围更大一圈的感知与估计」。不是谁更高级。
- 也不能因为改名叫算法组，就说计算机视觉过时了——自瞄这条链路上检测还是最前面那一环。
- 各队怎么叫是习惯问题，实际职责边界差异挺大，看别人仓库别被组名骗了。

## 2. 计算机视觉的定义

讲义列了三个来源，值得并排放着看：

| 来源 | 说法的大意 | 强调点 |
| --- | --- | --- |
| Stanford CS231A | 研究一套工具和理论，让机器能从图像、视频里提取有用信息，最终解释世界 | 工具与理论；目标是「解释世界」 |
| IEEE Technology Navigator | 人工智能与电气工程里的一个领域，使机器从图像/视频/其他视觉输入里提取有意义信息 | 学科归属与输入形式 |
| Szeliski《Computer Vision: Algorithms and Applications》 | 用计算方法，从一幅或多幅图像里推断、描述、重建现实世界及其属性 | 计算方法；重建世界属性 |

- **共性**：都是从「视觉观测」里拿到有用信息，再拿去分析、推断、理解。
- **差异**：CS231A 偏「工具箱 + 解释世界」；IEEE 偏「这是哪个学科的什么领域」；Szeliski 偏「用什么手段、要还原出什么」。
- 所以不存在一个全学科唯一、排他的定义。写文档时引用哪个都行，但要说清上下文。
- 我自己的说法：**计算机视觉 = 把图像这种数据，变成对现实世界有用的结论。**

## 3. 计算机视觉研究什么

### 3.1 视觉观测有哪些形式

- **图像**：某一时刻的二维视觉信息，最常用。
- **视频**：按时间排列的帧序列，多了「随时间怎么变」这一维。
- **深度图**：每个像素带距离；不过「深度」的具体定义取决于传感器和生成方式（结构光？双目？ToF？），不能想当然。
- **其他**：双目/多目、多光谱、事件相机等等。
- 关键一句：程序拿到的永远只是**数表**。一张 1280×1024 的彩色图就是 1280×1024×3 个数，每格 0~255。
- 这些数里并不自带「装甲板」「数字 3」「红色」这些概念，概念是人（或者训练出来的模型）贴上去的。
- 再补一句：图像不是现实世界本身，而是现实世界经过观测和成像之后的一份数据表示。**观测会丢信息**，这点后面一直要用。

### 3.2 想从观测里拿到的「目标信息」

同一块装甲板，能问的问题其实是分层的：

1. **它是什么** —— 是不是装甲板？数字是几？→ 识别 / 分类。
2. **它在哪里** —— 中心点、四个角点的图像坐标 → 定位。
3. **它离多远** —— 相对相机的三维位置 → 成像模型与空间几何。
4. **它什么姿态** —— 正对相机还是转了一个角 → 位姿估计。
5. **它怎么动** —— 连续帧里的位置变化与运动状态 → 多时刻观测 + 滤波。

- 这五层难度递增，但底层都依赖「像素坐标准不准」，所以第一讲死磕检测不是没道理。

### 3.3 典型研究问题

- 图像分类、目标检测、图像分割、关键点检测、深度估计、位姿估计、目标跟踪、三维重建。
- 这些任务**不严格互斥**：检测里可以顺手做关键点，分割也能拿来当检测用。
- 落地场景：自动驾驶、工业质检、医学影像、AR、机器人（我们就在这一类里）。

## 4. 在 RoboMaster 里视觉到底干什么

自瞄整条链，讲义给得挺清楚，我记成流水线：

```
图像 + 采集时间
   → 检测（类别、图像位置、特征点）
   → 位姿解算（相对相机的位置与朝向）
   → 坐标变换（结合云台姿态统一到同一坐标系）
   → 跟踪与状态估计
   → 瞄准与开火判定（延迟、弹道、执行机构约束）
   → 通信，交给电控
```

- 第一讲**只讲检测**这一环，后面的解算、跟踪、判定都是后面几讲的事。
- 检测的输出不是「这里有个装甲板」这么一句话，而是**灯条四个角点的像素坐标**，还要带上时间戳。
- 为什么强调角点：后面位姿解算要拿这四个点的对应关系去解 PnP，点错了后面全歪。
- 时间戳不能丢：链路每一步都有延迟，开火判定要算总延迟。

## 5. 图像是怎么来的（成像）

- 链路：光 → 镜头成像 → 传感器在有限面积、有限曝光时间内积分 → 读出电信号并数字化 → 颜色重建 → 到程序里变成数组。
- **同一个物体不会对应固定的像素值**。照明变了、角度变了、曝光变了，数值就变了。所以阈值不能当物理常量用。
- 镜面反光能亮过灯条本身，于是「最亮的区域」并不一定是目标。
- 焦距决定视场和像素尺度（我们常用定焦 6mm / 8mm）。**对焦**是「清晰的那个物距范围」，和变焦不是一回事；失焦就是糊，糊了轮廓就不好。
- 光圈数 ≈ 焦距 / 入瞳直径。光圈数越小 = 光圈越大 = 进光越多 = 景深越浅。
- 曝光是**积分**不是瞬时采样，所以有运动拖影：拖影长度 ≈ v · t。1000 px/s 下，5 ms 曝光约 6 px，1 ms 约 1.2 px。灯条本身才十几个像素宽，几个像素的拖影已经会改变轮廓宽度、方向和端点位置了。
- 增益只是把信号放大，不会增加光子；模拟增益和数字增益还不一样，噪声表现不同。
- 曝光拉长画面更亮，但不等于细节更多：红灯条中心会趋白（过曝），蓝灯条中心会偏青。**显示上提亮不等于拿到了更多光信号**。
- 全局快门 vs 滚动快门：滚动快门是逐行曝光，运动和闪光下会出现倾斜/弯曲；换成全局快门能消掉这种几何畸变，但**消不掉运动模糊**。

## 6. 数字图像基础

- 坐标约定：左上角是原点，x 向右增大，y 向下增大，像素坐标是整数、从 0 开始。
- 这个约定是写在「数据怎么解释」里的，数组本身不会告诉你哪个方向是 y。搞反了就是转置。
- (x, y) 对应数组里的第 y 行第 x 列——即 `img[y, x]`。
- 灰度是 1 通道，彩色是 3 通道；OpenCV 读彩色默认是 **BGR**，不是 RGB。
- 8 位无符号：取值 0~255，类型写作 `CV_8UC3`（彩色）/ `CV_8UC1`（灰度）。
- 内存估算：1920×1080×3 = 6220800 字节 ≈ 6.2 MB。实际还要考虑行步长与对齐；而 PNG/JPG 的文件大小是**压缩后**的概念，跟内存占用不是一回事。
- 二值掩膜里只有 0 和 255，但仍然是每像素 1 字节，并不会因为「只有两种值」就省 8 倍。
- 颜色是重建出来的：一个感光单元只能测一种颜色分量，Bayer 排列是 2×2 里 2 绿 1 红 1 蓝，缺的靠去马赛克插值补。
- 通道顺序必须和滤色阵列 / 采集接口的约定对上。RGB 和 BGR 混用最坑：程序不报错、照样跑，但红色被当成蓝色。验证办法是拿一个**已知颜色**的物体，把三个通道的数值打出来看。
- 到我们手里之前，图像还过了白平衡、颜色校正、非线性映射（gamma）、降噪、锐化、压缩。视频还多一层编码（H.264、YUV420），所以解码出来的颜色和原始传感器值不是一回事。
- ROI（感兴趣区域）：只处理一块能省算力、也能排除干扰。**注意坐标系换了**：ROI 内坐标以 ROI 左上角为原点，回原图要加偏移。例如 ROI 左上角是 (100, 60)，ROI 内的点 (12, 8) 在原图是 (112, 68)。如果 ROI 还做过缩放，要先把缩放恢复，再加偏移。

## 7. 颜色差与阈值分割

- 只按亮度筛不行：白色灯管在灰度图里比灯条还亮。讲义给的实测是灰度 > 200 的像素里，灯管框内有 3051 个，灯条框内只有 432 个。「足够亮」只能当候选条件，不能当判据。
- 区别在通道关系：白色区域三个通道数值接近，红色区域 R 明显大于 B。
- 于是定义**红色分数** = 饱和差 `max(R − B, 0)`。蓝色目标同理用 `B − R`。
- 讲义给的几个实测数值（B, G, R → 分数）：(21, 57, 226) → 205；(212, 255, 254) → 42；(0, 3, 35) → 35；(1, 14, 15) → 14。可以看到近白像素的分数很小，红色像素的分数很大。
- 掩膜 = 「颜色差 > 60」**且**「R > 100」→ 255，否则 0。两个都是严格大于。加 R > 100 这一步是为了排除暗处的小色差噪声（本例 980 个像素里筛掉 32 个）。
- 有个现象要注意：灯条中心接近白色，颜色差小，所以掩膜出来是**空心的框**，不是实心条。后面做几何的时候会吃这个亏。
- 阈值不是越高越好：提到 140，第 120 帧还能出 1 个候选，第 0 帧就一个都没有了；前 300 帧里阈值 60 每帧恰好 1 个候选，阈值 140 只有 125 帧能出。
- 结论：**单帧成功不代表参数可靠**，要跨帧、跨录像统计。

## 8. 形态学处理

- 结构元素用 3×3 方形，锚点居中。
- **腐蚀**：结构元素覆盖的范围内全是前景才保留 → 前景缩小、细连接断开。
- **膨胀**：只要碰到一个前景就点亮 → 前景扩张、小缺口被填。
- **开运算** = 先腐蚀再膨胀：去掉小前景块和细窄连接，整体尺寸大致不变。
- **闭运算** = 先膨胀再腐蚀：补小缺口、把邻近区域连起来。
- 本例的坑：掩膜是空心框，两侧有些地方只有 2 个像素宽。3×3 开运算直接把左灯条切成约 32 px 和 19 px 两段，于是变成 3 根候选灯条、配不成对，整段视频没输出。
- 换成闭运算，细窄连接被保住，左灯条约 55 px、右灯条约 61 px，配对成功。**讲义的基线是闭运算**。
- 掩膜一开始有 9 个连通区域（2 个灯条 + 左灯条附近 4 个碎块 + 远处 3 个小区域），闭运算之后剩 5 个。
- 远处那些小区域的轮廓面积只有 0~8.5 px²，最后是靠「面积 ≥ 20」这个几何条件排除的。
- 所以分工是：**形态学负责让区域成形、连通，几何筛选负责判断它像不像灯条**。两者别混着调。

## 9. 轮廓与几何

- 连通性用 8 邻域：上下左右 + 四个对角都算相连。
- 我们只取外轮廓（`RETR_EXTERNAL`），不保留孔洞，所以空心框和实心条可能给出**一样的外轮廓**。
- 轮廓本身只是边界点集，它不知道什么是「灯条」，语义是后面加上的。
- `minAreaRect` 是能包住轮廓、面积最小、允许旋转的矩形。它给出：长边（灯条长度 l）、短边（宽度 w）、中心 c、长轴单位向量 u。
- 端点公式：`上 = c − u·l/2`，`下 = c + u·l/2`。
- **这里有个容易错的地方**：端点是长轴的端点，不是「两条长边的中点」。竖着的长矩形，两条长边的中点在左右两侧，它们的连线是沿短轴方向的。
- 合成数据的验证例：11 列 × 81 行的像素块，理论宽 10、长 80，前景像素 891 个，但轮廓面积算出来是 800。差在「像素是格子、面积按像素中心算」。所以**轮廓面积 ≠ 前景像素个数**。
- 讲义的筛选阈值（左右灯条实测值）：

| 条件 | 阈值 | 左灯条 | 右灯条 |
| --- | --- | --- | --- |
| 轮廓面积 | ≥ 20 | 286.5 | 558 |
| 长度 | ≥ 6 | 55.0 | 61.0 |
| 长宽比 | ≥ 2 | 6.1 | 5.5 |
| 偏离竖直 | ≤ 35° | 0.0° | 0.0° |

- 这些数字都依赖图像尺寸、目标距离、分割方式，**不是装甲板的普遍定义**。换相机换场地就得重新看。

## 10. 灯条配对

两根灯条单独看都合格，还得证明它们是同一块装甲板的两侧。讲义用了四个条件：

| 条件 | 表达式 | 阈值 | 主例实测 |
| --- | --- | --- | --- |
| 长度接近 | max(l₁,l₂) / min(l₁,l₂) | ≤ 1.5 | 1.11 |
| 高度接近 | \|Δy\| / 平均长度 | ≤ 0.35 | 0.19 |
| 间距合适 | 中心距 / 平均长度 | 0.8 ~ 3.2 | 2.44 |
| 方向接近 | 两长轴夹角 | ≤ 15° | 0.0° |

- 用平均灯条长度做归一化，是为了让「高度差」和「间距」这两个条件在缩放时大致保持不变——远处小目标的两根灯条，绝对像素间距小得多，但比值差不多。
- 但别把它说成「与距离姿态完全无关」：透视会压缩比例，转角会改变比值，检测误差也会。只是**近似**不变。
- 配对通过后，把四个端点按顺序连起来，还要求围成的四边形面积 ≥ 1 px²，排除退化（四点几乎共线那种）。
- 四点顺序的规定：按中心横坐标分左右，0 = 左灯条上端，1 = 右灯条上端，2 = 右灯条下端，3 = 左灯条下端。
- 注意这四个点是**灯条长轴的端点**，不是分类外扩区域的角，也不是金属底板的四个角。后面 PnP 用的就是这四个点，所以顺序必须固定。

## 11. 失败分析：第 668 帧

- 现象：Red_5000 第 600 帧正常，第 668 帧检测不到。
- 查下来是配对环节：高度差比算出来 > 0.35，被拒了。
- 只把阈值放宽到 0.5，这一帧能救回来，但别的帧会多出一堆错误组合。局部修一个 bug 要验证整体。
- 排查方法值得记：**按阶段看实际输出**，不要一上来就调阈值。
  1. 输入里到底有没有有效目标信息？
  2. 颜色分数算得对不对？
  3. 掩膜和连通结构长什么样？
  4. 灯条筛选还是配对把东西拒了？
- 日志要记「被拒绝时的具体数值」，只打印「候选数 = 0」是查不出原因的。

## 12. 总结

- 这一讲的主线是一条很朴素的流水线：**成像 → 数据表示 → 颜色分割 → 区域处理 → 几何组合**。
- 每一步都在丢信息、也在加约束，最后剩下的东西才勉强能叫「装甲板」。
- 课上演示基本用 OpenCV 现成函数（threshold / morphologyEx / findContours / minAreaRect），理解参数比自己写算法更要紧。
- 讲义自己也说了，这只是**最基础**的一套检测流程。真实比赛里还有各种问题（曝光变化、遮挡、多个目标、数字识别……）。

## 14. 我的疑问 / 待深入

1. **阈值到底怎么定才不心虚？** 讲义说 60 和 140 在不同帧上表现差很多。有没有一套「在多少帧、多少段录像上通过才算过」的流程，而不是盯着单帧调？
2. **空心框到底要不要填？** 现在靠闭运算把空心框连成一个连通区域，再用外轮廓。如果改用填充孔洞（fill holes），面积和长宽比会不会更稳、更不容易被开运算切碎？
3. **高度差条件该用哪个方向？** 讲义写的是 |Δy| / 平均长度，那是灯条竖直时的写法。我理解应该改成「沿灯条长轴方向的分量」，倾斜时才不会被误杀。这个改动在什么情况下会失效？
4. **滚动快门和运动模糊对端点精度的影响有多大？** 拖影几个像素，四点坐标就偏几个像素，PnP 解出来差多少？这个误差量级还没概念。
5. **如果灯条颜色接近白色**（比如曝光过度、或者对面装甲板本来就是白色），颜色差这条路是不是就废了？那时候该换什么特征？
